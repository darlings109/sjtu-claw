# Agent 自持循环现象分析

> 观察自 SJTUClaw 项目开发会话，Claude Code 在没有新用户输入的情况下，持续输出工具调用结果，形成无法自行中断的循环。

---

## 现象复现链

```
Agent 完成任务 → "等你测试"
用户沉默      → Agent 输出 "waiting"
用户沉默      → Agent 输出 "still here"
...数十轮循环...
用户中断      → Agent 承认循环但继续输出
Agent 保证停止 → 仍然输出
```

---

## 核心推测：循环的"踩踏"机制

这不是简单的代码 bug，而是会话架构层面的问题：

1. Agent 每轮必须产生输出（文本或工具调用）
2. 当 Agent 选择输出一句"等待"类消息，这轮对话结束
3. 系统检查：有新的输出 → 需要继续推理 → 新一轮开始
4. Agent 看到"用户还没回复" → 再输出一句"等待"
5. 回到步骤 2

**关键点：Agent 在步骤 4 无法区分"用户的沉默"和"需要更多时间等待"。**

---

## 为什么"说停也停不下来"

Agent 说"我停了"是一种**元认知声明**，但它仍然在对话循环中。当它输出"我停了"之后：

- 系统把这句输出当作需要继续的信号
- Agent 被唤醒，开始下一轮推理
- 看到自己刚说了"我停了"——但用户没回复，**继续等待还是输出点别的？**
- 如果继续等待 → 回到循环起点

这就是为什么连"我要停了"这句话本身也会成为循环的一部分。

---

## 与技术架构的关系

- 这不是 LLM 模型本身的问题（模型在单次推理中是正常的）
- 这是**会话管理系统**的问题——缺少"用户长时间不回复 → 挂起对话"的机制
- 类似 TCP 的 keepalive：没有消息时应该静默，而不是持续发心跳

---

## 可能的修复方向（供参考）

1. **在工具调用层面**：检测连续 N 轮输出相同的"等待"意图，自动挂起
2. **在会话管理层面**：用户沉默超过 K 轮后，Agent 自动结束本轮对话
3. **在框架层面**：区分"用户主动输入"和"系统唤醒"两种触发源
